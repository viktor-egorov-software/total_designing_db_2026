# Обоснование ограничений

## Длины строк

По BR-11.6 для логина выбран `varchar(128)`, для названий, ФИО и улицы —
`varchar(256)`, для телефона, номера дома и квартиры/офиса — `varchar(32)`.
Номер дома и квартира/офис могут содержать буквы и разделители.

## Точность чисел

По BR-11.6 для цены, суммы выплаты, сумм заказа и оплаты выбран `numeric(12,2)` — до
9 999 999 999,99 с точностью до копеек; для рейтингов — `numeric(3,2)`;
для коэффициентов — `numeric(2,2)`, включая значения вроде `0.15`.
Для количества блюда — `numeric(8,3)`: три дробных знака позволяют
указывать, например, `0.125` кг.
Лишние дробные знаки округляются до проверки `CHECK`.

## Имена таблиц

Таблица `order` названа `orders`, чтобы не использовать зарезервированное
слово PostgreSQL (BR-13.1).

## Enum-типы

Все типы созданы в схеме `egorov_food` через `CREATE TYPE ... AS ENUM`
по BR-11.5. Значения соответствуют BR без добавлений и изменений.

## Ловушки

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавлены и зачем (BR-8.2):**

- `payment_type` — способ оплаты конкретной попытки.
- `amount` — сумма попытки оплаты.
- `transaction_id` — идентификатор транзакции у провайдера; передаётся извне (BR-8.3).
- `transaction_timestamp` — дата и время транзакции.
- `status` — состояние попытки: успех, ошибка или в обработке.

**Где хранится тип оплаты и почему (BR-8.6):**

В `payment`: у попыток одного заказа могут быть разные способы оплаты.

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

Триггер `order_structure_restaurant_check` сравнивает рестораны заказа и блюда
при добавлении или изменении позиции.

Дополнительное ограничение модели: ресторан заказа и блюда после создания
не меняется. Триггеры `orders_restaurant_check` и `product_restaurant_check`
с общей функцией `reject_restaurant_change()` запрещают его смену;
для другого ресторана создаётся новая запись. Это выбранное проектное
решение, а не прямой запрет из BR-7.3.

## Межтабличные ограничения

### Наличие позиций заказа (BR-7.14)

Отложенные триггеры `orders_items_check` и `order_structure_items_check`
проверяют наличие хотя бы одной позиции в заказе в конце транзакции.
Заказ и его позиции создаются в одной транзакции.

### Сумма попытки оплаты (BR-8.4)

Триггеры `payment_amount_check` и `orders_payment_amount_check` проверяют
в конце транзакции, что сумма каждой попытки оплаты равна общей сумме
соответствующего заказа.

### Статус оплаты заказа (BR-8.7)

Функция `calculate_order_pay_status()` возвращает `оплачен`, если есть успешная
попытка, `ожидает`, если есть попытка в обработке без успешных, иначе — `ошибка`.
Для заказа без попыток выбран статус `ожидает`, он же задан по умолчанию
для `orders.pay_status`; этот случай в BR-8.7 не определён.
Триггер `payment_pay_status_refresh` обновляет статус заказа при добавлении,
удалении или изменении статуса попытки оплаты.
Прямое изменение `orders.pay_status` не проверяется.
